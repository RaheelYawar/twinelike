- **`exits` / `exit` identifier** is unimplemented. Reference Harlowe (see the `exits` getter in `ts/section.ts`) reports the number of clickable interactive elements currently on screen — used in patterns like `(if: exits is 0)[Game over]`. Implementing it cleanly requires a live re-evaluation model: the count changes mid-render as interactive elements are added, and reference's eval engine re-runs expressions after each add. Our impl doesn't have live re-evaluation; adding it is a substantial slice that's adjacent to the `(live:)` / `(event:)` work in the candidate-next-slices list. `turns` / `turn` was the easy half and shipped; `exits` defers until the live system lands.
- **Elided comparison `is < 5`** is unimplemented. Reference Harlowe lets authors chain comparisons against an implicit operand carried through `and`/`or` chains — `(if: $a is 5 and is < 10)` means "$a is 5 and $a < 10". Reference's runner.ts (`getElisionOperands` plus the `isComparisonOp` walker) detects when an `and`/`or` sibling is a comparison and propagates its LHS across the chain, including ambiguity-error handling for `is not` chains. A parser-only rewrite to `it < 5` looks tempting but produces silently wrong results — our `it` slot updates only on `Set`, not after each comparison, so the elided form would compare against stale state. Proper implementation needs evaluator changes to track comparison LHS across `and`/`or` operands. Defer until the rest of the comparison/logic plumbing settles.

- **Engine-wide non-finite-number policy is undecided (latent, low).** The evaluator does unguarded IEEE-754 double arithmetic, so NaN/±Infinity flow through expressions the way they do in JS (which mostly *matches* reference, since reference is also JS doubles): `NaN + 1` is NaN, `NaN < 1` is false, `(num: "Infinity")` is +∞. `(min:)`/`(max:)` handle NaN explicitly (any NaN → NaN, matching `Math.min`/`Math.max`) so their fold isn't order-dependent — but there's no engine-wide stance on whether non-finite values should be *rejected* at their source (e.g. division by zero, `∞ − ∞`). Reference permits them; we currently do too. Decide a policy (permit-and-propagate, as now, vs. reject-at-source with an in-prose error) before a feature surfaces the need — `(num:)` already rejects NaN strings, so the surface is inconsistent.
- ✅ **FIXED (2026-07-15) — A non-string `start` in StoryData was silently dropped (real bug, edge; confirmed 2026-07-12).** `ApplyStoryData` read `start` via `AsString`, so `{"start":123}` yielded null, `StartNode` stayed `"0"`, and the story rendered a blank first passage with no diagnostic. **Fix:** `TweeReader.StartName` coerces scalar `start` values (number/bool) to their JSON text — number formatting mirrors `JsonWriter`'s, whole values without `.0` — and feeds the same passage-lookup gate a string start uses; structured values (object/array) can't be passage names and stay unresolved. See `StoryData_NumericStart_*`/`StoryData_StructuredStart_*` in `TweeReaderTests`.
- ✅ **FIXED (2026-07-15) — `RenamePassage` corrupted inbound links when the new name contained link metacharacters (real bug; found 2026-07-12 audit).** `RewriteInboundLinks` substituted the new name raw into every rewritten `[[…]]`, so renaming to `A->B`/`A<-B`/`New]]evil` silently retargeted or broke all three link forms, written straight into `RawBody`. **Fix:** the rename is refused (returns false, nothing mutated) when `updateInboundLinks` is set and the new name contains a link separator — `->`, `<-`, `|`, or `]]` (`ContainsLinkSeparator`; `|` included because pipe links parse now and the rightmost-`|`-wins rule re-splits any rewritten target carrying one). `updateInboundLinks: false` still permits such names as a pure index re-key. See `RenamePassage_NewNameWithLinkSeparator_*` in `HarloweEditingTests`.
- ✅ **FIXED (2026-07-15) — Empty-string style values emitted malformed CSS (real bug, low).** `(text-colour: "")` and `(font: "")` passed `StyleValueValidator` and landed in the HTML adapter as `color: ;` / `font-family: ;` (it gates on `!= null`, not emptiness); only `(background:)` errored, via its own check. **Fix:** the validator rejects an empty/whitespace-only value up front with `(background:)`'s existing message (`value is empty`), so all three string-taking style macros agree and no spec is created carrying nothing; `BackgroundMacro`'s own now-unreachable empty check was removed. See `EmptyStyleValue_EmitsErrorAndDoesNotPushStyle` in `StylingMacroTests`.

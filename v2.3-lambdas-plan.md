# v2.3 — Lambdas + Lambda-Consuming Macros

Forward-looking implementation plan. Once each sub-slice ships, its summary folds into `CLAUDE.md` and the corresponding section here is deleted.

**Shipped:** v2.3A (lambda foundation + `(find:)` + `(all-pass:)`), v2.3B (`via` clause + `(altered:)` + `(some-pass:)` + `(none-pass:)`), v2.3D (`each` + `(for:)` body iteration; descriptor-patch `Changer` refactor). See `CLAUDE.md` Roadmap for landed-state summaries.

**Remaining:** v2.3C (`making` clause + `(folded:)` + `(rotated-to:)`), v2.3E (`(sorted:)`). Both reuse the existing foundation.

## Goal

After v2.3, Harlowe stories doing collection operations or list rendering work end-to-end on this library — the 9 lambda-consuming macros that don't depend on additional infrastructure (HookName matchers, event/live system, custom `(macro:)`).

## Sub-slices

### 2.3C — `making` + `(folded:)` + `(rotated-to:)`

**Lands:**
- Parser: extend `ParseLambdaTail` to recognise the two-parameter `_running making _x via ...` shape. The first variable (leading parameter) becomes `LambdaNode.ParameterName`; after consuming `making`, the next variable becomes `MakingName`; then required `via` introduces `ViaClause`.
- `LambdaInvoker.EvalFold` — binds both `it` (to the item) and the accumulator name and the item name, evaluates `ViaClause`, returns the new accumulator value. Uses the same shared `EvaluateClause` discipline as predicate/transform.
- `(folded:)` macro — reduce. First arg is a fold lambda; remaining args are items (auto-iterate single trailing array via `LambdaArgs.ExpandItems`). Initial accumulator comes from the first item (Harlowe's documented behaviour — empty input errors in-prose). Returns the final accumulator value.
- `(rotated-to:)` macro — predicate-driven rotation. First arg is a `where` lambda; remaining args are items. Find the first item that matches; rotate the array so that item is at index 1. If no match, return the array unchanged. Uses `LambdaInvoker.EvalPredicate`.

**Tests:** fold initial/empty/single-item, accumulator-shadows-temp scope-isolation, `(rotated-to:)` various pivot positions including no-match.

### 2.3E — `(sorted:)`

**Lands:**
- `(sorted:)` macro with two arities:
  - No-lambda: default ordering — string-aware over strings, numeric over numbers. Mixed-kind input errors in-prose.
  - With lambda: 2-parameter `via` form returning a comparison number (negative/zero/positive in C# `Comparer<T>` convention). The lambda's two parameters need a parser-level decision — Harlowe writes it as `_a, _b via ...` or similar. Settle in the slice.

No new parser work for the no-lambda arity. The lambda arity may need a small parser extension if the two-parameter form isn't already covered by `making` (likely is — `making` syntactically binds two names).

**Tests:** default sort over numbers/strings, custom comparator (ascending and descending), mixed-kind input errors out, empty input → empty array, single-item is identity.

## Cross-cutting concerns

### MarkupPrinter

`MarkupPrinter.Visit(LambdaNode)` already handles every shape — the canonical forms in source match the round-trip output:

- `_x where _x > 5`
- `_x via _x * 2`
- `_running making _x via _running + _x`
- `each _x`
- `where it > 5` (implicit-it)

Round-trip tests live in `MarkupPrinterRoundTripTests`. v2.3C adds tests for the `making` shape; v2.3E adds tests for `(sorted:)` with and without a comparator lambda.

### Error propagation

Same discipline as v2.3A/B: lambda evaluation errors short-circuit, consuming macro returns the error, `IRenderOutput.Error` surfaces it. `LambdaInvoker.*` methods restore scope via `using` so a clause-internal error can't leak bindings.

## What v2.3 doesn't ship and why

- **No HookName/revision macros** (`(click:*)`, `(change:)`, `(enchant:)`). They take lambdas, but lambda is the smallest piece — they need named-hook targeting and click event dispatch. Their own slice. With v2.3D's descriptor-patch model, they slot in as new `IChangerPatch` types.
- **No event/live system** (`(event:)`, `(live:)`, `(trigger:)`). Async re-evaluation is its own architecture.
- **No custom `(macro:)`**. Explicitly advanced per Harlowe docs; lower-priority for typical stories.
- **No `(unpack:)`**. Destructuring is a different surface; share parser DNA with lambdas but not strictly part of v2.3.
- **No `...` spread operator.** Today `LambdaArgs.ExpandItems` auto-unpacks a single trailing array as a workaround. Adding real spread is a parser+evaluator extension that's orthogonal to v2.3.

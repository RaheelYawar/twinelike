# Harlowe Parser — C# Library

## Project Overview
A C# library (netstandard2.0) for parsing and running Twine/Harlowe interactive fiction stories. Targets game engines (Unity, Godot, etc.) as the primary consumer — they implement `IRenderOutput` to drive whatever text-rendering layer they have (TextMeshPro tags, BBCode, plain text, etc.). Accepts both Twine 2 HTML exports and Twee 3 source; emits Twee 3 back out.

## Build & Run
- **Framework:** Library targets `netstandard2.0` for maximum consumer reach (Unity 2018.1+, Godot 3/4, .NET Framework 4.6.1+, .NET 5+, Mono, Xamarin). Test project targets `net48`. Both are SDK-style csprojs.
- **Build:** `dotnet build Twinelike.sln`
- **Test:** `dotnet test Twinelike.sln`
- **Output:** Library DLL (`harlowe_parser.dll`)
- The library csproj sits at the repo root and uses `<DefaultItemExcludes>` to keep it from globbing the test folder.

## Architecture
- Entry points: `new Harlowe(htmlText)` for the Twine 2 HTML export, or `new TweeReader().Read(tweeText)` for the plain-text Twee 3 form. Both paths populate the same `Harlowe` story object. Outbound: `new TweeWriter().Write(story)` emits Twee 3 source (the only write format; HTML emit is out of scope, since Twine 2 is the natural HTML producer).
- Two parsing layers. **Layer 1 (host)** has two front-ends: HtmlAgilityPack extracts `<tw-storydata>` / `<tw-passagedata>` from HTML and HTML-entity-decodes the inner text via `HtmlEntity.DeEntitize`; `TweeReader` splits Twee source on `:: Name [tags] {position}` headers at column 0, special-cases `:: StoryTitle` and `:: StoryData` (with a hand-rolled `JsonReader`), and synthesizes sequential pids since Twee has none. **Layer 2 (Harlowe markup)** is shared: `HarloweTokenizer` → `HarloweBodyParser` (which delegates to `HarloweExpressionParser` at every `MacroOpen`) → `PassageBody` AST stored on `HarlowePassage.Ast`. `HarlowePassage.Body` (string) and `HarlowePassage.Branches` are derived from the AST by visitors. Both front-ends populate `HarlowePassage.RawBody` so `TweeWriter` can emit clean passages verbatim (lazy reserialization — only passages whose `IsDirty` flag is set re-canonicalize via `MarkupPrinter`).
- The AST splits node types between **body** (prose, hooks, links, command macros — `IBodyNode`) and **expression** (macro arguments — `IExpressionNode`). Same `(name: ...)` syntax can become either `MacroNode` or `MacroCallNode` depending on position, which is why the split exists. Both trees use the visitor pattern.
- The tokenizer (`HarloweTokenizer`) covers every `TokenType` and every Harlowe operator from the manual's precedence table — including multi-word operators (`is not`, `is in`, `is a`, `does not contain`, etc.) fused at lex time, the whitespace-sensitive `'s`, the digit-leading `2bind`, and the `-type` TypedVar suffix. It uses a mode stack of `Frame { Mode, ParenDepth }` (Body vs. Expression with per-frame paren depth so `)` is disambiguated as `ParenClose` vs `MacroClose`) and an `_inLink` flag that suppresses macro/hook markup inside `[[…]]`.
- Parsers live in `HarloweParser/Parsing/`. Both share a `TokenCursor` so the body parser can hand the cursor to the expression parser at every macro-arg list. `HarloweExpressionParser` is precedence-climbing using the manual's operator order (lower order = tighter binding); all binary ops are left-associative and `and`/`or` share order 13.
- Branch links use Harlowe's `[[display text->passage name]]` syntax. Because `HtmlEntity.DeEntitize` runs before tokenization, the tokenizer sees raw `->` rather than the `-&gt;` it would otherwise be encoded as.
- **Runtime layer** lives under `HarloweParser/Runtime/`. Pipeline: `ExpressionEvaluator` (an `IExpressionVisitor` returning `HarloweValue`) and `BodyRenderer` (an `IBodyVisitor` pushing through `IRenderOutput`) share a `MacroContext` (variable store, RNG, pending-goto flag, last-conditional flag, render-passage callback). `MacroRegistry` is a flat name→`IMacro` directory that also implements `IMacroInvoker` so the evaluator can dispatch nested `MacroCallNode`s. The `to`/`into` assignment operators are handled by the evaluator (mutate via `IVariableStore`); `(set:)`/`(put:)` are nearly no-op macros because the work has already happened by the time the registry sees them. `(if:)`/`(unless:)`/`(else:)` write `LastConditional` on the context; the body renderer reads it to decide hook rendering and resets it after any non-conditional macro so `(else:)` only pairs with the immediately preceding conditional. Errors propagate as `HarloweValue.Error` through the evaluator (every operator short-circuits) and exit through `IRenderOutput.Error` rather than thrown exceptions.
- **Changer architecture** is descriptor-patch (matches the reference Harlowe JS impl). A `Changer` carries a flat list of `IChangerPatch` objects; each patch mutates a fresh `HookDescriptor` (Styles + Iteration + Revision + Interaction) when the changer applies. The renderer then executes the finished descriptor — interaction wraps + handler registration if `Interaction` is set, else splices into the render tree if `Revision` is set, else loops if `Iteration` is set, else push/render/pops the accumulated styles. Style-only changers like `(text-style:)` produce a `StylePatch`; `(for:)` produces an `IterationPatch`; `(replace:)`/`(append:)`/`(prepend:)` produce a `RevisionPatch`; the click/hover macros produce an `InteractionPatch`. `Changer.Apply`'s `renderHook` is `Action<IRenderOutput>` — usually handed the live output, but for revision/interaction a detached `RenderTreeBuilder` so the source can be spliced (or, for interaction, stashed until the dispatched event fires). `Changer.ApplyTo(IRenderContainer, Enchantment source = null)` is the dual entry point used by `(change:)`/`(enchant:)`: instead of producing content for a hook, it wraps an *already-rendered* node's children in the changer's style layers; the optional source tag lets the enchantment pass re-run idempotently.
- **Render tree** (`Runtime/Rendering/`) sits between `BodyRenderer` and `IRenderOutput` — an addressable, mutable representation of rendered passage content (the analogue of the reference impl's `<tw-hook>` DOM). `BodyRenderer` renders into a `RenderTreeBuilder`, which *is* an `IRenderOutput` (so `Changer.Apply` retargets onto the tree for free — a changer's `PushStyle` becomes a `RenderStyleNode` with no changer-code change) plus `BeginHook`/`EndHook` and `BeginInteractive`/`EndInteractive` for the channels `IRenderOutput` adds at the structural boundary. `RenderTreeFlusher` walks the finished tree and replays the identical event stream at the real output. `RenderHookNode` is the addressable unit (anonymous hooks still get one, with a null name); `RenderInteractiveNode` carries an `InteractiveRegion` and brackets a click/hover region; `HookResolver.Resolve` is the `selectHook` analogue (`?passage`/`?page`→root, `?link`→links, named→hooks); `TextOccurrenceFinder` wraps literal substring matches as addressable hooks for string-target revision. Revision macros mutate the tree (splice rendered source into resolved targets); `RenderNode.Clone` keeps each target's splice independent so the tree stays a tree.
- **Enchantments** are persistent restylings. `(enchant: ?target, changer)` registers an `Enchantment` on `MacroContext.Enchantments`; `StorySession` runs `EnchantmentPass.Update` over the finished tree after each render and after every dispatch (the `updateEnchantments()` analogue). The pass is **idempotent**: it `Disenchant`s first — unwrapping every `RenderStyleNode` tagged with a `SourceEnchantment` — and then re-applies, so running it any number of times against a mutated tree leaves a single, correct application. `(change:)` is the one-shot sibling: it `ApplyTo`s immediately at the point it runs against the tree built so far; its style wraps carry no source tag and survive across passes.
- **Interactive channel + dispatch.** `IRenderOutput` brackets click/hover regions with `BeginInteractive(InteractiveRegion)` / `EndInteractive()` — symmetric with `PushStyle`/`PopStyle`. Each click/hover macro (`(click:)`, `(click-append:)`, `(mouseover-prepend:)`, …) wraps its `?target` matches in a `RenderInteractiveNode` and registers a `ClickHandler` on `MacroContext.ClickHandlers` keyed by the wrap's region id. Composed style layers (`(click-append: ?m) + (text-style: "bold")`) become `RenderStyleNode`s around the interactive node, each tagged with the same region id via `SourceRegionId` so the dispatch unwrap removes them alongside the interactive wrap — the target returns to its pre-interaction styling and the appended content lands unstyled. The session keeps the live tree + handlers alive between renders; the host engine reports a user event through `StorySession.DispatchEvent(regionId)`, which fires the handler — unwraps the consumed region (interactive node + region-tagged style wraps), renders the deferred hook into a detached builder, splices a `RenderNode.Clone` into every re-resolved target via the revision machinery, re-runs the (idempotent) enchant pass, and re-flushes. No whole-passage re-render. All matches of one `(click:)` call share a single region id so re-resolution at dispatch hits every current match. Handlers are single-use. A `(goto:)` inside a deferred hook navigates via `Goto` after dispatch finishes.
- **Lambda layer**: `Ast.Expression.LambdaNode` covers every Harlowe lambda permutation (`where`/`via`/`making`/`each` + implicit-`it`) via nullable clause fields. `HarloweValueKind.Lambda` + `LambdaValue` wrap the AST as an opaque runtime value (reference equality — authors rarely compare). `LambdaInvoker` is the shared utility every lambda-consuming macro routes through: binds the parameter + `it` slot per item via `IVariableStore.PushBinding`/`PushItBinding` (IDisposable scope-restore), evaluates the relevant clause through a fresh `ExpressionEvaluator`, restores on dispose. Lambdas see the caller's store at invocation time, no closure capture.
- All source lives in `HarloweParser/`; data models are simple public-field classes.

## Key Files
- `HarloweParser/Harlowe.cs` — Main entry point: metadata extraction, passage indexing, AST wiring. Editing API: story-level fields (`StoryName`, `StartNode`, `Creator`, `CreatorVersion`, `Ifid`, `Format`, `FormatVersion`, `StoryDataExtras`) have public setters; public parameterless ctor for from-scratch construction; `AddPassage(passage)` (auto-synthesizes pid when null/empty), `RemovePassage(name)`, `RenamePassage(oldName, newName)` (re-keys the lookup), and `Passages` enumerator.
- `HarloweParser/BodyVisitors.cs` — internal `BranchCollector` and `BodyTextRenderer` `IBodyVisitor` implementations used by both the HTML loader and `TweeReader` to derive `HarlowePassage.Branches` and `HarlowePassage.Body` from the AST. Each exposes a static one-shot helper (`Collect(ast)` / `Render(ast)`). Previously duplicated as private nested classes in `Harlowe.cs` and `TweeReader.cs`; centralized so a new body-AST node only needs one `Visit` override per visitor across the codebase.
- `HarloweParser/HarlowePassage.cs` — Passage model (Pid, Name, Body, Tags, Branches, Ast, RawBody, Position, IsDirty).
- `HarloweParser/Twee/` — Twee 3 read + write. `TweeReader` (header parsing + body routing through the existing tokenizer/body parser), `JsonReader` and `JsonWriter` (hand-rolled minimal JSON for the `:: StoryData` special passage; pretty-printed output; avoids dragging Newtonsoft/System.Text.Json into consumer projects), `MarkupPrinter` (`IBodyVisitor`+`IExpressionVisitor` walking AST back to canonical Harlowe markup; precedence-driven parens; smart-quoted strings with throw-on-both-quotes pending tokenizer escape support), and `TweeWriter` (story → Twee text; lazy reserialization via `HarlowePassage.IsDirty`; overlays typed StoryData fields onto `Harlowe.StoryDataExtras` so unknown JSON keys round-trip; re-escapes body lines starting with `::` to `\::`).
- `HarloweParser/Branch.cs` — Link model (Text, Name).
- `HarloweParser/Tokens/` — `ITokenizer`, `Token`, `TokenType`, and `HarloweTokenizer` (full implementation including all Harlowe operators, multi-word fusion, `'s`, `2bind`, `-type`).
- `HarloweParser/Parsing/` — `TokenCursor`, `IExpressionParser`/`HarloweExpressionParser` (precedence-climbing), `IBodyParser`/`HarloweBodyParser` (recursive descent with hook attachment via whitespace-skipping lookahead).
- `HarloweParser/Ast/Body/` — Body AST nodes (`MacroNode`, `HookNode`, `LinkNode`, `TextNode`, `NewlineNode`, `VariableNode`, `HtmlNode`, `ChangerChainNode`, `PassageBody`) with `IBodyVisitor`. `ChangerChainNode` carries an expression (typically a `+`-chain of `MacroCallNode`s or a `VariableRefNode`) plus an optional attached hook — the runtime evaluates the expression, applies as a Changer if the result is one, otherwise falls back to value-then-hook.
- `HarloweParser/Ast/Expression/` — Expression AST nodes (`LiteralNode`, `IdentifierNode`, `VariableRefNode`, `BinaryOpNode`, `UnaryOpNode`, `MacroCallNode`, `ArrayNode`, `DatamapNode`, `DatasetNode`, `LambdaNode`, `HookRefNode`) with `IExpressionVisitor`. `LambdaNode` carries nullable clause fields (Where/Via/When + Making accumulator + `IsEach`) — one node covers every Harlowe lambda shape. `HookRefNode` is a `?name` reference (a value in macro args, distinct from a `|name>[…]` hook declaration) carrying `Steps` — the ordinal narrowing folded from chained `'s` accessors (`?cake's 1st`).
- `HarloweParser/Runtime/` — Runtime. `HarloweValue`/`HarloweValueKind` (tagged union with `Error`, `Changer`, `Lambda`, `HookName` variants), `IVariableStore`/`HarloweVariableStore` (story+temp namespaces, `it` slot, deep-copy snapshots; `PushBinding`/`PushItBinding` IDisposable scope helpers for lambda binding), `ExpressionEvaluator` (visitor returning `HarloweValue`, error short-circuit on every operator), `IEvaluationContext` (`time`/`visits`/`passage` for the evaluator), `IMacroInvoker` (decouples evaluator from registry), `IMacro`/`MacroContext`/`MacroRegistry`, `IRenderOutput`/`BufferedRenderOutput`/`HtmlRenderOutput`, `BodyRenderer`, `RenderResult` (output DTO), `StyleSpec` (semantic styling description), `InteractiveRegion` + `InteractionKind` (the bracketing payload on `IRenderOutput`), `LambdaValue` (opaque AST wrapper), `LambdaInvoker` (shared bind+evaluate for `where`/`via` clauses), `HookDescriptor` + `IChangerPatch`/`StylePatch`/`IterationPatch`/`RevisionPatch`/`InteractionPatch` (descriptor-patch changer model), `HookNameValue` (opaque `?name` selector spec — a lazily-resolved query), `Enchantment` + `EnchantmentPass` (persistent restyling registered by `(enchant:)`, idempotent disenchant + re-apply), `ClickHandler` (the per-region deferred-hook + revision spec the session fires on `DispatchEvent`), and `StorySession` (top-level engine surface, including `DispatchEvent`).
- `HarloweParser/Runtime/Rendering/` — render tree layer. `RenderNode` (+ `Clone` for revision/dispatch splicing) + concrete nodes (`RenderTextNode`/`RenderHtmlNode`/`RenderLinkNode`/`RenderErrorNode`/`RenderStyleNode` (carries `SourceEnchantment` tag for idempotent disenchant and `SourceRegionId` tag so composed style wraps unwrap with their interactive region at dispatch)/`RenderHookNode`/`RenderInteractiveNode`/`RenderRoot`; container nodes implement `IRenderContainer`; `RenderNodes` static clone helpers), `RenderTreeBuilder` (an `IRenderOutput` that builds the tree, plus `BeginHook`/`EndHook` and `BeginInteractive`/`EndInteractive`), `RenderTreeFlusher` (walks the tree, replays the flat event stream), `HookResolver` (`selectHook` analogue: `?passage`/`?page`→root, `?link`→link nodes, named→`RenderHookNode`s, then ordinal-step narrowing), `TextOccurrenceFinder` (wraps literal substring matches as fresh anonymous `RenderHookNode`s so string-target revision has a splice point).
- `HarloweParser/Runtime/Macros/` — macro implementations, one class per file: `SetMacro`, `PutMacro`, `PrintMacro`, `IfMacro`, `ElseMacro`, `UnlessMacro`, `GotoMacro`, `DisplayMacro`, `RandomMacro`, `EitherMacro`, `AMacro`, `DmMacro`, `ModuloMacro`, `TextMacro`, `NumMacro`, `HistoryMacro`, `TextStyleMacro` (changer), `FindMacro`, `AllPassMacro`, `AlteredMacro`, `SomePassMacro`, `NonePassMacro`, `ForMacro`, `FoldedMacro`, `RotatedToMacro`, `SortedMacro` (lambda-consuming), `ReplaceMacro`, `AppendMacro`, `PrependMacro` (revision changers, sharing `RevisionChangers.Build`), `ChangeMacro`, `EnchantMacro` (enchantment commands, sharing `EnchantmentMacroSupport.Validate`), and the click/hover family — `ClickMacro`/`ClickReplaceMacro`/`ClickAppendMacro`/`ClickPrependMacro` + `MouseOver*`/`MouseOut*` mirrors, all grouped in `InteractionMacros.cs` since each is a Kind+Mode pair over the shared `InteractionChangers.Build`. `StandardMacros.RegisterAll(registry)` wires them onto a fresh registry. `LambdaArgs.ExpandItems` auto-unpacks a single trailing array (workaround for deferred `...` spread).
- `HarloweParser/Runtime/Changer.cs` — descriptor-patch changer primitive. Internal `List<IChangerPatch>`; `Compose(other)` concatenates patch lists; `Apply(output, renderHook, ctx)` builds a fresh `HookDescriptor` by running each patch, then executes — splices into the live render tree via `RevisionSpec` if present (`RunRevision`: render hook into a detached builder with composed styles wrapping it, resolve target via `HookResolver`/`TextOccurrenceFinder`, splice a `Clone` per match), else loops via `IterationSpec` (binding lambda param + `it` per item), else push/render/pops the accumulated style layers once. `FromStyle`/`FromIteration`/`FromRevision` are the factories; future changer kinds add new patches without changing `Apply`. `Layers` property preserved for diagnostics (projects through a descriptor).
- `HarloweParser/Runtime/StyleSpec.cs` — semantic styling description. Public-field class with named flags + value fields, structural equality, `IsEmpty` shortcut. Engine-agnostic shape — no HTML coupling.
- `HarloweParser/Runtime/HtmlRenderOutput.cs` — adapter `IRenderOutput` that wraps an inner output and translates `PushStyle`/`PopStyle` events into HTML tags. Bold/italic/underline/strike alone fold to short tags (`<b>`/`<i>`/`<u>`/`<s>`); any value field present collapses to a single `<span style="...">` carrying inline CSS. Static `EscapeAttribute` HTML-escapes user-supplied values before embedding into the attribute. Web consumers wrap their output in this; tests asserting HTML output route the same way.
- `HarloweParser.Tests/` — direct tests for tokenizer, expression parser, body parser, end-to-end HTML/Twee parsing, runtime (value/store/evaluator/registry/renderer/session), changer pipeline, render tree (`Runtime/Rendering/` — builder/flusher flush-parity + `HookResolver`), macros (v1 set + lambda-consuming + `(text-style:)` + `(for:)` + revision + enchantment + interaction/dispatch), and Twee read/write/markup-print round-trips.
- `TestFiles/testFile.html` — sample Harlowe story (8 passages; some links target absent passages — useful for testing tolerant parsing).

## Code Conventions
- **Namespace:** `Harlowe`
- **Indentation:** 2 spaces
- **Braces:** Allman style (opening brace on its own line)
- **Private fields:** `_camelCase` prefix
- **Public properties:** PascalCase; use expression-bodied members where concise (e.g., `=> _passages.Count`)
- **Data models:** Use public fields (not properties) for simple DTOs (`HarlowePassage`, `Branch`)
- **Null handling:** Return `null` or `string.Empty` for missing lookups, not exceptions
- **No LINQ usage** — the codebase uses explicit loops and Dictionary lookups

## Error Policy
In-prose errors, never exceptions. Mirrors Harlowe's authoring model: a single bad expression renders an inline error message at the spot it happened and the rest of the passage continues. `HarloweValue.Error` propagates through the evaluator (every operator short-circuits on it); when an Error value reaches the renderer it goes through `IRenderOutput.Error(message)` instead of being printed. No exceptions on the runtime hot path — engine integrations don't want `try/catch` around every render call.

## Known TODOs
- Tokenizer string literals do not handle escape sequences (`\"`, `\\`). Load-bearing for `MarkupPrinter`: a string containing both `"` and `'` cannot be round-tripped — the printer throws `HarloweParseException` rather than emit un-reparseable output. Once tokenizer escapes land, switch `MarkupPrinter.AppendStringLiteral` to always-double-quote with backslash escapes and drop the smart-quoting branch.
- `BodyTextRenderer` (in `BodyVisitors.cs`) drops `MacroNode` content from the rendered body string. Acceptable for current consumers; if a downstream needs macros in the rendered prose, add a printer that round-trips macros via the AST.
- (Resolved) `to`/`into` are now restricted at parse time to the top of `(set:)`/`(put:)` argument lists; see `HarloweExpressionParser.IsAssignmentMacro` and the `allowAssignmentAtTop` plumbing in `ParseBinary`. Sub-expressions and other macros surface `HarloweParseException` on a stray assignment, so the prior "evaluation-time leak" hazard is gone. The existence pre-checks in `BodyRenderer.Visit(MacroNode)` and `ExpressionEvaluator.Visit(MacroCallNode)` are kept for clean error messages only.

## Status

**v3.1 complete, 1135 tests passing, no active slice.** Full per-version implementation history is in `git log` — see commit messages tagged by slice. The current shape rests on three load-bearing architectural pivots; everything else in the codebase is built atop them and any future slice should respect them rather than work around them.

- **Descriptor-patch changer model** (introduced v2.3D, matches the reference Harlowe JS impl). A `Changer` is a flat `List<IChangerPatch>` over a `HookDescriptor`. New changer kinds drop in as new patch types + descriptor fields — `Apply` never grows a new top-level branch you can't isolate. Style/Iteration/Revision/Interaction all slot in this way.
- **Render tree between `BodyRenderer` and `IRenderOutput`** (introduced v3A). An addressable, mutable representation of rendered content, so revision and enchantment macros have something concrete to target rather than a one-way event stream. `RenderTreeBuilder` *is* an `IRenderOutput`, which is why `Changer.Apply` retargets onto the tree for free.
- **Semantic event channels on `IRenderOutput`** (v2.2 styles, v3D interactive). `PushStyle`/`PopStyle` and `BeginInteractive`/`EndInteractive` are the bracketing primitives game engines map to their native UI — TMP `<link>` + `<b>`, BBCode `[url]` + `[b]`, HTML `<a>` + `<span>`. The interface is the engine-integration contract and should grow additively, by adding parallel bracket pairs, not by reshaping existing methods.

## Candidate next slices

No active slice; this is a candidate list, not a queue. Weigh each against the game-engine audience before defaulting to order.

- **Event/live system** — `(event:)`, `(live:)`, `(trigger:)`. Needs async/live re-evaluation, plus a tick callback channel from the engine to the session.
- **More styling changers (second wave)** — `(border:)`/`(border-colour:)`/`(border-size:)`/`(corner-radius:)`/`(rotate:)`/`(text-indent:)`/`(text-rotate-x/y/z:)`. Follow the same `StylePatch` pattern as v3.1; borders take CSS-shorthand sided args (1=all, 4=t/r/b/l).
- **`(hover-style:)` and `(line-style:)`/`(char-style:)`/`(link-style:)`** — need a pseudo-state field on the descriptor and per-line/char/link tree iteration respectively. Their own slice.
- **String-target click/hover** — `(click: "some text")[…]`, analogous to string-target revision. Reuses `TextOccurrenceFinder`; deferred from v3D to keep scope tight.
- **`(link:)` family** — `(link-replace:)`, `(link-reveal:)`, `(link-goto:)`. Interaction macros that *create* new link elements rather than wrapping existing hooks. Reuses v3D's interactive channel.
- **Story-wide `(enchant:)`** via `header`/`footer`-tagged passages. Needs cross-passage enchantment threading on `StorySession`.
- **Transitions** — `(t8n:)`, `(transition:)`, `t8n-depart`/`t8n-arrive`. Slot in as another `IChangerPatch` per the v2.3D model; engine consumers need a transition descriptor channel.
- **Custom `(macro:)` + `(output:)`** — author-defined macros. Explicitly advanced per Harlowe docs; lower priority for typical stories.
- **Convenience syntax** — property assignment (`(set: $person's name to "Bob")`), `(unpack:)` destructuring, `...` spread, storylets, dataset evaluation. Authors can work around all with longer forms; quality-of-life rather than capability.

# Harlowe Parser — C# Library

## Project Overview
A C# library (netstandard2.0) for parsing and running Twine/Harlowe interactive fiction stories. Targets game engines (Unity, Godot, etc.) as the primary consumer — they implement `IRenderOutput` to drive whatever text-rendering layer they have (TextMeshPro tags, BBCode, plain text, etc.). Accepts both Twine 2 HTML exports and Twee 3 source; emits Twee 3 back out.

## Build & Run
- **Framework:** Library targets `netstandard2.0` for maximum consumer reach (Unity 2018.1+, Godot 3/4, .NET Framework 4.6.1+, .NET 5+, Mono, Xamarin). Test project targets `net48`. Both are SDK-style csprojs.
- **Build:** `dotnet build Twinelike.sln`
- **Test:** `dotnet test Twinelike.sln`
- **Output:** Library DLL (`harlowe_parser.dll`)
- The library csproj sits at the repo root and uses `<DefaultItemExcludes>` to keep it from globbing the test folder.

## Spec & reference sources
When a design question turns on how Twine/Twee/Harlowe is *supposed* to behave, fetch and quote the authoritative source before recommending a fix — don't reason from "what seems reasonable" or "what other tools probably do."

- **Twee 3 / serialization questions** → the Twee 3 specification at `github.com/iftechfoundation/twine-specs` (maintained by the IFTechFoundation, which stewards Twine itself — closest to "official").
- **Harlowe macro/runtime semantics** → reference Harlowe source is checked into this repo at `references/harlowe-branch-default.zip` (snapshot of the canonical Mercurial repo at `foss.heptapod.net/games/harlowe`, branch `default`). Unzip to `/c/temp` or similar and read `ts/macrolib/*.ts` for macro semantics, `ts/internaltypes/*.ts` for runtime types. The Heptapod host itself sits behind Anubis bot-protection that blocks automated fetches — if `references/` is stale, ask the user to re-download via browser. Quote the relevant TypeScript, don't paraphrase.
- **Cross-tool compatibility claims** → check at least one popular implementation (Tweego at `github.com/tmedwards/tweego`, Extwee at `github.com/videlais/extwee`) before claiming "tools generally do X."

Use `gh api -H "Accept: application/vnd.github.raw" repos/<owner>/<repo>/contents/<path>` to fetch raw files — WebFetch has session limits. Distinguish authority levels in recommendations: the IFTF-maintained spec is closest to "official"; third-party compilers are popular but not authoritative.

**Don't write line numbers** into docstrings or code comments when citing reference source — they rot when the reference repo updates (`ts/twinescript/runner.ts:668` is dead the moment runner.ts gains or loses a few lines upstream). Cite by file path + a quoted identifier or short phrase the reader can grep for ("the `ws` pattern in `ts/markup/patterns.ts`", "see `varref.ts`'s `set()` parent-walk loop"). The grep stays valid through refactors; the line number doesn't.

When quoting reference Harlowe's regex character classes (e.g. the `ws` pattern in `ts/markup/patterns.ts`) into C# XML doc comments, **do not paste the literal Unicode characters** — U+2028 (LINE SEPARATOR) and U+2029 (PARAGRAPH SEPARATOR) are treated as line breaks by the C# lexer, which silently truncates the surrounding `///` comment block and turns the trailing characters into stray code tokens (CS1519). Spell the code points out as text (`U+2028`, `U+202F`, etc.) instead.

Real example: the `\::` body-content escape in `TweeWriter` looked like a normal Twee feature worth fixing symmetrically — checking the spec + Tweego + Extwee revealed it's a library-local extension nobody else implements, which flipped the recommendation from "fix the asymmetry" to "document and leave."

## Architecture
- Entry points: `new Harlowe(htmlText)` for the Twine 2 HTML export, or `new TweeReader().Read(tweeText)` for the plain-text Twee 3 form. Both paths populate the same `Harlowe` story object. Outbound: `new TweeWriter().Write(story)` emits Twee 3 source (the only write format; HTML emit is out of scope, since Twine 2 is the natural HTML producer).
- Two parsing layers. **Layer 1 (host)** has two front-ends: HtmlAgilityPack extracts `<tw-storydata>` / `<tw-passagedata>` from HTML and HTML-entity-decodes the inner text via `HtmlEntity.DeEntitize`; `TweeReader` splits Twee source on `:: Name [tags] {position}` headers at column 0, special-cases `:: StoryTitle` and `:: StoryData` (with a hand-rolled `JsonReader`), and synthesizes sequential pids since Twee has none. **Layer 2 (Harlowe markup)** is shared: `HarloweTokenizer` → `HarloweBodyParser` (which delegates to `HarloweExpressionParser` at every `MacroOpen`) → `PassageBody` AST stored on `HarlowePassage.Ast`. `HarlowePassage.Body` (string) and `HarlowePassage.Branches` are derived from the AST by visitors. Both front-ends populate `HarlowePassage.RawBody` so `TweeWriter` can emit clean passages verbatim (lazy reserialization — only passages whose `IsDirty` flag is set re-canonicalize via `MarkupPrinter`).
- The AST splits node types between **body** (prose, hooks, links, command macros — `IBodyNode`) and **expression** (macro arguments — `IExpressionNode`). Same `(name: ...)` syntax can become either `MacroNode` or `MacroCallNode` depending on position, which is why the split exists. Both trees use the visitor pattern.
- The tokenizer (`HarloweTokenizer`) covers every `TokenType` and every Harlowe operator from the manual's precedence table — including multi-word operators (`is not`, `is in`, `is a`, `does not contain`, etc.) fused at lex time, the whitespace-sensitive `'s`, the digit-leading `2bind`, and the `-type` TypedVar suffix. String literals are cooked at lex time: the JS-spec escape set (`\n` `\r` `\t` `\b` `\f` `\v` `\0` `\\` `\'` `\"` `\xHH` `\uHHHH`) is decoded into the token's `Value` so the runtime/printer never sees raw escape sequences; unknown escapes drop the backslash (matches reference Harlowe via its JS evaluator). It uses a mode stack of `Frame { Mode, ParenDepth }` (Body vs. Expression with per-frame paren depth so `)` is disambiguated as `ParenClose` vs `MacroClose`) and an `_inLink` flag that suppresses macro/hook markup inside `[[…]]`.
- Parsers live in `HarloweParser/Parsing/`. Both share a `TokenCursor` so the body parser can hand the cursor to the expression parser at every macro-arg list. `HarloweExpressionParser` is precedence-climbing using the manual's operator order (lower order = tighter binding); all binary ops are left-associative and `and`/`or` share order 13.
- Branch links use Harlowe's `[[display text->passage name]]` syntax. Because `HtmlEntity.DeEntitize` runs before tokenization, the tokenizer sees raw `->` rather than the `-&gt;` it would otherwise be encoded as.
- **Runtime layer** lives under `HarloweParser/Runtime/`. Pipeline: `ExpressionEvaluator` (an `IExpressionVisitor` returning `HarloweValue`) and `BodyRenderer` (an `IBodyVisitor` pushing through `IRenderOutput`) share a `MacroContext` (variable store, RNG, pending-goto flag, last-conditional flag, render-passage callback). `MacroRegistry` is a flat name→`IMacro` directory that also implements `IMacroInvoker` so the evaluator can dispatch nested `MacroCallNode`s. The `to`/`into` assignment operators are handled by the evaluator (mutate via `IVariableStore`); `(set:)`/`(put:)` are nearly no-op macros because the work has already happened by the time the registry sees them. `(if:)`/`(unless:)`/`(else:)` write `LastConditional` on the context; the body renderer reads it to decide hook rendering and resets it after any non-conditional macro so `(else:)` only pairs with the immediately preceding conditional. Errors propagate as `HarloweValue.Error` through the evaluator (every operator short-circuits) and exit through `IRenderOutput.Error` rather than thrown exceptions.
- **Changer architecture** is descriptor-patch (matches the reference Harlowe JS impl). A `Changer` carries a flat list of `IChangerPatch` objects; each patch mutates a fresh `HookDescriptor` (Styles + Iteration + Revision + Interaction) when the changer applies. The renderer then executes the finished descriptor — interaction wraps + handler registration if `Interaction` is set, else splices into the render tree if `Revision` is set, else loops if `Iteration` is set, else push/render/pops the accumulated styles. Style-only changers like `(text-style:)` produce a `StylePatch`; `(for:)` produces an `IterationPatch`; `(replace:)`/`(append:)`/`(prepend:)` produce a `RevisionPatch`; the click/hover macros produce an `InteractionPatch`. `Changer.Apply`'s `renderHook` is `Action<IRenderOutput>` — usually handed the live output, but for revision/interaction a detached `RenderTreeBuilder` so the source can be spliced (or, for interaction, stashed until the dispatched event fires). `Changer.ApplyTo(IRenderContainer, Enchantment source = null)` is the dual entry point used by `(change:)`/`(enchant:)`: instead of producing content for a hook, it wraps an *already-rendered* node's children in the changer's style layers; the optional source tag lets the enchantment pass re-run idempotently.
- **Render tree** (`Runtime/Rendering/`) sits between `BodyRenderer` and `IRenderOutput` — an addressable, mutable representation of rendered passage content (the analogue of the reference impl's `<tw-hook>` DOM). `BodyRenderer` renders into a `RenderTreeBuilder`, which *is* an `IRenderOutput` (so `Changer.Apply` retargets onto the tree for free — a changer's `PushStyle` becomes a `RenderStyleNode` with no changer-code change) plus `BeginHook`/`EndHook` and `BeginInteractive`/`EndInteractive` for the channels `IRenderOutput` adds at the structural boundary. `RenderTreeFlusher` walks the finished tree and replays the identical event stream at the real output. `RenderHookNode` is the addressable unit (anonymous hooks still get one, with a null name); `RenderInteractiveNode` carries an `InteractiveRegion` and brackets a click/hover region; `HookResolver.Resolve` is the `selectHook` analogue (`?passage`/`?page`→root, `?link`→links, named→hooks); `TextOccurrenceFinder` wraps literal substring matches as addressable hooks for string-target revision. Revision macros mutate the tree (splice rendered source into resolved targets); `RenderNode.Clone` keeps each target's splice independent so the tree stays a tree.
- **Enchantments** are persistent restylings. `(enchant: ?target, changer)` registers an `Enchantment` on `MacroContext.Enchantments`; `StorySession` runs `EnchantmentPass.Update` over the finished tree after each render and after every dispatch (the `updateEnchantments()` analogue). The pass is **idempotent**: it `Disenchant`s first — unwrapping every `RenderStyleNode` tagged with a `SourceEnchantment` — and then re-applies, so running it any number of times against a mutated tree leaves a single, correct application. `(change:)` is the one-shot sibling: it `ApplyTo`s immediately at the point it runs against the tree built so far; its style wraps carry no source tag and survive across passes.
- **Interactive channel + dispatch.** `IRenderOutput` brackets click/hover regions with `BeginInteractive(InteractiveRegion)` / `EndInteractive()` — symmetric with `PushStyle`/`PopStyle`. Each click/hover macro (`(click:)`, `(click-append:)`, `(mouseover-prepend:)`, …) wraps its `?target` matches in a `RenderInteractiveNode` and registers a `ClickHandler` on `MacroContext.ClickHandlers` keyed by the wrap's region id. Composed style layers (`(click-append: ?m) + (text-style: "bold")`) become `RenderStyleNode`s around the interactive node, each tagged with the same region id via `SourceRegionId` so the dispatch unwrap removes them alongside the interactive wrap — the target returns to its pre-interaction styling and the appended content lands unstyled. The session keeps the live tree + handlers alive between renders; the host engine reports a user event through `StorySession.DispatchEvent(regionId)`, which fires the handler — unwraps the consumed region (interactive node + region-tagged style wraps), renders the deferred hook into a detached builder, splices a `RenderNode.Clone` into every re-resolved target via the revision machinery, re-runs the (idempotent) enchant pass, and re-flushes. No whole-passage re-render. All matches of one `(click:)` call share a single region id so re-resolution at dispatch hits every current match. Handlers are single-use. A `(goto:)` inside a deferred hook navigates via `Goto` after dispatch finishes.
- **Lambda layer**: `Ast.Expression.LambdaNode` covers every Harlowe lambda permutation (`where`/`via`/`making`/`each` + implicit-`it`) via nullable clause fields. `HarloweValueKind.Lambda` + `LambdaValue` wrap the AST as an opaque runtime value (reference equality — authors rarely compare). `LambdaInvoker` is the shared utility every lambda-consuming macro routes through: binds the parameter + `it` slot + 1-indexed `pos` slot per item via `IVariableStore.PushBinding`/`PushItBinding`/`PushPosBinding` (IDisposable scope-restore), evaluates the relevant clause through a fresh `ExpressionEvaluator`, restores on dispose. Lambdas see the caller's store at invocation time, no closure capture.
- All source lives in `HarloweParser/`; data models are simple public-field classes.

## Code Conventions
- **Namespace:** `Harlowe`
- **Indentation:** 2 spaces
- **Braces:** Allman style (opening brace on its own line)
- **Private fields:** `_camelCase` prefix
- **Public properties:** PascalCase; use expression-bodied members where concise (e.g., `=> _passages.Count`)
- **Data models:** Use public fields (not properties) for simple DTOs (`HarlowePassage`, `Branch`)
- **Null handling:** Return `null` or `string.Empty` for missing lookups, not exceptions
- **No LINQ usage** — the codebase uses explicit loops and Dictionary lookups

## Temp variable scoping
Temp variables (`_foo`) are hook-scoped via a stack of dictionaries inside `HarloweVariableStore`. Every `Visit(HookNode)` in `BodyRenderer` pushes a fresh scope; entry dies on hook exit. Set semantics walk outer-to-inner looking for an existing declaration and write to the OUTERMOST match (matches reference Harlowe's parent-walking `set()` loop in `ts/internaltypes/varref.ts`: "inner hooks can modify outer hooks' values"); fresh declarations land in the innermost scope. Story-scoped `$` vars are unaffected — they share a single flat dictionary. `(for:)` iterations get a fresh scope per iteration for free (each iteration re-renders the attached hook through the same `Visit(HookNode)` path).

## Error Policy
In-prose errors, never exceptions. Mirrors Harlowe's authoring model: a single bad expression renders an inline error message at the spot it happened and the rest of the passage continues. `HarloweValue.Error` propagates through the evaluator (every operator short-circuits on it); when an Error value reaches the renderer it goes through `IRenderOutput.Error(message)` instead of being printed. No exceptions on the runtime hot path — engine integrations don't want `try/catch` around every render call.

**Parse-error recovery.** Same in-prose contract extends to load time. Tokenizer/parser failures don't abort a story load — loaders (HTML, Twee, `AddPassage`) catch `HarloweParseException` and substitute a synthetic `ParseErrorNode` AST via `Harlowe.MakeParseErrorAst` so the rest of the story stays usable and the broken passage renders an in-prose error at render time. The body parser additionally recovers *per node*: a `HarloweParseException` inside `ParseNodes` is captured as a `ParseErrorNode`, then `TryAdvanceToResumePoint` advances the cursor to the next safe body-mode resync (newline or balanced macro-close) at the same hook depth so well-formed siblings after the failure still parse. `Harlowe.DecorateParseErrors` recursively prefixes nested ParseErrorNodes (inside hooks, attached hooks) with the passage name; `Harlowe.EnsureWholeStubOriginalSource` stashes the original source on a wholly-failed passage's stub so `TweeWriter` can round-trip even when `RawBody` is null. `TweeWriter.ResolveBody` distinguishes a wholly-stub AST (`ParseErrorNode.IsWhollyParseError` — single child) from partial recovery: the stub prefers `RawBody`; partial recovery follows the normal `IsDirty` path so consumer AST edits flow through `MarkupPrinter`.

## Known TODOs
- **Per-macro divergences** vs reference Harlowe are tracked in `MACRO-DIVERGENCES.md` at the repo root — 16 findings (5 high, 10 medium, 1 low) with concrete triggers and recommended ordering. Not duplicated here to avoid drift; treat that doc as the source of truth for macro-level gaps and this section for everything else.
- `BodyTextRenderer` (in `BodyVisitors.cs`) is now unused by the loaders (HTML/Twee/AddPassage all set `Body` to the raw author source). Keep for diagnostics or remove once no consumer references it.
- **`exits` / `exit` identifier** is unimplemented. Reference Harlowe (see the `exits` getter in `ts/section.ts`) reports the number of clickable interactive elements currently on screen — used in patterns like `(if: exits is 0)[Game over]`. Implementing it cleanly requires a live re-evaluation model: the count changes mid-render as interactive elements are added, and reference's eval engine re-runs expressions after each add. Our impl doesn't have live re-evaluation; adding it is a substantial slice that's adjacent to the `(live:)` / `(event:)` work in the candidate-next-slices list. `turns` / `turn` was the easy half and shipped; `exits` defers until the live system lands.
- **Elided comparison `is < 5`** is unimplemented. Reference Harlowe lets authors chain comparisons against an implicit operand carried through `and`/`or` chains — `(if: $a is 5 and is < 10)` means "$a is 5 and $a < 10". Reference's runner.ts (`getElisionOperands` plus the `isComparisonOp` walker) detects when an `and`/`or` sibling is a comparison and propagates its LHS across the chain, including ambiguity-error handling for `is not` chains. A parser-only rewrite to `it < 5` looks tempting but produces silently wrong results — our `it` slot updates only on `Set`, not after each comparison, so the elided form would compare against stale state. Proper implementation needs evaluator changes to track comparison LHS across `and`/`or` operands. Defer until the rest of the comparison/logic plumbing settles.
- **`--` comment family** is unimplemented. Reference Harlowe defines four related comment forms (documented in the `comment` rule of `ts/markup/patterns.ts`): (1) token-skip inside macro args — `(set: $x to --2 6)` deletes the `--` and the next token; (2) line comments — `-- prose` at line start drops prose up to the next non-prose boundary; (3) comment hooks `--[...]` — block comments, nestable, the most useful in real authoring; (4) HTML comments `<!-- ... -->` — likely already pass through because we forward HTML tags raw. The four layers touch different parts of the pipeline (tokenizer + expression parser for #1, body parser for #2 and #3) so each adds real surface. The practical subset is #1 + #3; the full feature is all four. Defer as a single "Comments" slice — implementing only one form would be a partial feature that authors find confusing.
- `(background:)` image-vs-colour heuristic is **inverted** from reference Harlowe (see the `["background", "bg"]` entry in `ts/macrolib/stylechangers.ts`). Reference rule: "colour only if hex / function-call shape; else image (default to `url(value)`)." Ours: "image only if URL prefix / image extension; else colour." Diverges on named CSS colours (`"blue"`, `"navy"`) — we treat as colour, reference treats as image URL — and on extensionless paths. Reference's design presumes authors pass a typed `Colour` value (from `(rgb:)`/`(hsl:)`/`(lch:)`) for named colours; we don't have a typed `Colour` runtime value yet so we picked the more author-intuitive default. Re-aligning would require landing a typed `Colour` first.
- **Unified recursion ceiling.** Reference Harlowe uses a single 50-frame stack cap covering hook nesting, `(display:)`, `(for:)` iteration, lambda evaluation, AND consecutive `(goto:)`s — see the `this.stack.length >= 50` check in `ts/section.ts`. Ours uses separate per-axis caps: `MaxGotoDepth=20`, `MaxDisplayDepth=20`/`AbsoluteMaxDisplayDepth=256`. Different stories hit limits in different impls. Our per-axis model is arguably more debuggable (the error message tells the author which axis ran away), but error reporting diverges and a story tuned against reference's unified cap could behave differently here. Migration would mean retiring the per-axis counters in favour of a single `MacroContext.StackDepth` incremented at every recursion point.
- **`TwineError` type discrimination.** Reference's `TwineError` (see `ts/internaltypes/twineerror.ts`) carries a typed kind — `syntax`, `operation`, `macrocall`, `datatype`, `custommacro`, `infinite`, `property`, `unimplemented`, `propagated`, `user`, `assertion`, `debugonly` — each with a distinct default explanation. `(assert:)`, debug mode, and error propagation all branch on the type. Our `HarloweValue.Error` carries just a string; two errors with identical messages but different conceptual kinds are indistinguishable. Add a kind enum (or string tag) when a feature surfaces the need — debug mode and `(assert:)` are the natural triggers.
- **`(history:)` returns undo-stack order, not Moment-timeline order.** Reference Harlowe's `(history:)` walks the `Moment[]` timeline (`ts/state.ts`). Ours iterates the undo stack via `_undoStack.ToArray()` — same answer for single-redirect navigations, but a passage that fires multiple `(goto:)`s in one turn collapses to a single undo entry in ours and to multiple Moments in reference. Resolves once the save-model slice lands a real Moment timeline.
- **Non-ASCII Unicode digits crash the loader (real bug, not a divergence).** The tokenizer's number-literal dispatch gates on `char.IsDigit` (the digit branch in the main tokenize switch and the `while`/`if` guards in `ScanNumberLiteral`), and `char.IsDigit` returns true for non-ASCII decimal digits — Arabic-Indic (U+0660–0669), fullwidth (U+FF10–FF19), Devanagari, etc. So a body like `(print: ٥)` or `(set: $x to ５)` emits a `NumberLiteral` token carrying the non-ASCII digit string, and `ParseAtom`'s `double.Parse(t.Value, CultureInfo.InvariantCulture)` then throws `FormatException` (InvariantCulture only accepts `0`–`9`). The loaders (`HydratePassageFromBody`, the HTML/Twee front-ends) catch only `HarloweParseException`, so the `FormatException` escapes and aborts the entire story load — a direct violation of the "in-prose errors, never exceptions" error policy. Fix: restrict the digit gate to ASCII `'0'..'9'` so Unicode digits fall through to identifier/text handling, matching reference Harlowe, whose number rule (the `\d` in `ts/markup/patterns.ts`) is ASCII-only. (Alternative: switch `ParseAtom` to `double.TryParse` and substitute a `ParseErrorNode` on failure — but the ASCII gate is the cleaner match to reference.) Smallest of the candidate bug-fixes; do this first.
- **`(click:)`/`(replace:)` families silently no-op on `?link` targets (real bug).** `HookResolver.Resolve` matches `?link` to `RenderLinkNode`s, but `RenderLinkNode` doesn't implement `IRenderContainer`, so `Changer`'s interaction wrap loop and `Splice` both skip every match (`if (!(targets[i] is IRenderContainer container)) continue;`, and the same guard in `Splice`). `(click: ?link)[…]` registers no handler and never fires; `(replace:/append:/prepend: ?link)` does nothing — all with no diagnostic, even though the resolver documents `?link` as a supported target. Fix: either make `RenderLinkNode` a container (give it children carrying its text) or special-case link wrapping in the interaction/revision paths. Distinct from the string-target click/hover candidate slice (that's `(click: "literal")`); this is the hook-name `?link` selector.
- **Passage names aren't escaped on Twee write nor unescaped on read (real bug, round-trip data loss).** `TweeWriter.AppendHeader` emits `passage.Name` raw (tags go through `AppendEscapedTag`; names don't), and `TweeReader.ParseHeader` stops the name at the first raw `[`/`{` without decoding `\[`/`\{`/`\\`. A passage named `Choose [A]` writes `:: Choose [A]` and re-reads as name `Choose` plus a bogus tag block `[A]`; a spec-compliant `:: Choose \[A\]` reads as name `Choose \`. The Twee 3 spec requires escaping `[ ] { } \` in passage names (verified against the IFTF spec + Tweego/Extwee). Fix symmetrically: escape those characters in `AppendHeader` and strip the escapes in `ParseHeader`'s name scan, mirroring the existing tag-escape pair.
- **`RenamePassage` leaves inbound `[[…->oldName]]` links dangling (real bug).** It re-keys the name lookup and `_passageOrder` and sets `passage.Name`, but never rewrites `Branch.Name` on other passages (branches are derived once at load), so every link / `(goto:)` targeting the old name resolves to null at render time, with no diagnostic at rename. (Pid-based `StartNode` is unaffected; name-based references are not.) Fix: on rename, walk all passages' `Branches` (re-deriving from AST where needed) updating matching targets — or explicitly document that link rewriting is the caller's responsibility.
- **Body-parser error recovery can swallow a well-formed sibling macro (real bug).** `TryAdvanceToResumePoint` resyncs on the first depth-0 `MacroClose` with no notion of which macro owns it. When an error is thrown *after* `ParseArgumentList` already consumed the failing macro's own `)` — e.g. the chain-position assignment-macro check in `ParseMacro` that rejects `(set:)`/`(put:)` as changer-chain components — the resync scans forward and consumes the *next* macro's `)`, folding that valid sibling into the `ParseErrorNode`. Trigger: `(set: $x to 5) + (print: 1) tail` loses `(print: 1)`, leaving only ` tail`. Same root cause as the documented nested-malformed-macro edge above; the real fix is threading macro-call depth through the body parser so the catch knows how many `MacroClose` tokens the broken construct owns.
- **Hand-rolled `JsonReader` has no recursion-depth cap (real bug, uncatchable crash).** `ReadValue` → `ReadObject`/`ReadArray` → `ReadValue` recurses without limit, so a deeply nested `:: StoryData` body (e.g. thousands of `[`) throws an uncatchable `StackOverflowException` and kills the host — `TweeReader.Read` catches only `HarloweParseException`. Adversarial input only, but it bypasses the in-prose error policy. Fix: track nesting depth in `ReadValue` and throw a normal `HarloweParseException` past a sane ceiling.
- **`Set` aliases collections by reference — no clone-on-set (latent bug).** `HarloweVariableStore.Set` stores the `HarloweValue` reference directly, so `(set: $b to $a)` makes `$a` and `$b` share one backing `List`/`Dictionary`. No shipped macro mutates a stored collection in place, so it's invisible today, but it will bite the moment property-assignment (`(set: $a's 1st to …)`), `(move:)`, etc. land. Reference clones on set when the value already has a knownName (`ts/internaltypes/varref.ts`'s `set()`). Fix alongside (or before) the property-assignment slice: deep-copy Array/Datamap values on `Set`.
- **Twee header position metadata is delimited by the first `}` (real bug, edge).** `ParseHeader` uses `line.IndexOf('}', p)`, so JSON metadata containing `}` inside a nested object or a string value is truncated and the leftover `}` leaks into further header parsing. Position is stored opaque and re-emitted verbatim, so the corruption round-trips out. Twine's flat `{"position":…,"size":…}` avoids it; custom/nested metadata triggers it. Fix: brace-match (respecting strings) instead of first-`}`, or parse the block with `JsonReader`.
- **No pid-uniqueness check in `AddPassage` or the HTML loader (real bug, edge).** Only passage *name* uniqueness is enforced (via `Dictionary.Add`); two passages can share a pid (a hand-edited HTML export with duplicate `pid=`, or an explicit `Pid` colliding with a synthesized one — `NextAvailablePid` only avoids collisions with *existing numeric* pids). `GetPassageByPid` / `GetStartPassage` then returns whichever enumerates first from the unordered dictionary, so resolution is non-deterministic across runtimes on a story that loaded without error. Fix: validate pid uniqueness on `AddPassage`/`Parse` (error, or re-synthesize on collision).
- **A `(goto:)` loop hitting the depth ceiling leaves session state polluted (real bug, edge).** Each hop calls `EnterPassage` (which bumps `_visitCounts` and advances `_currentPassage`) *before* the recursive `RenderInternal`; the `depth >= MaxGotoDepth` check fires only at the top of the next frame. So on abort `CurrentPassage` is some intermediate passage, every cycle passage's `(visits)` is inflated, and no undo snapshot was taken for the intra-render hops — the host gets the "too many redirects" error but the session is left inconsistent. Adjacent to the unified-recursion-ceiling TODO above; fix by checking depth *before* `EnterPassage` and/or restoring `_currentPassage`/visit counts on abort.
- **A non-string `start` in StoryData is silently dropped (real bug, edge).** `ApplyStoryData` reads `start` via `AsString` (`v as string ?? fallback`), so `{"start":123}` (number/bool/null) yields null, `pendingStartName` stays null, and `StartNode` is never set — the story silently loses its start passage rather than coercing or erroring. Fix: coerce non-string scalars, or surface a diagnostic when `start` is present but unusable.

## Status

**v3.1 + divergence-audit pass shipped, 1294 tests passing, no active slice.** Full per-version implementation history is in `git log` — see commit messages tagged by slice. The audit pass (run against the canonical reference Harlowe source in `references/harlowe-branch-default.zip`) closed nine concrete divergences with user-visible impact (hook-scoped temp variables, `=` as `to`, `%` modulo, polymorphic `+`/`-`, lambda `pos` + `str` alias, `turn`/`turns` identifier, `incorrectOperator` hints, right-associative `of`) and filed the architectural-scale remainder under `Known TODOs` and `Candidate next slices`.

The current shape rests on four load-bearing architectural pivots; everything else in the codebase is built atop them and any future slice should respect them rather than work around them.

- **Descriptor-patch changer model** (introduced v2.3D, matches the reference Harlowe JS impl). A `Changer` is a flat `List<IChangerPatch>` over a `HookDescriptor`. New changer kinds drop in as new patch types + descriptor fields — `Apply` never grows a new top-level branch you can't isolate. Style/Iteration/Revision/Interaction all slot in this way.
- **Render tree between `BodyRenderer` and `IRenderOutput`** (introduced v3A). An addressable, mutable representation of rendered content, so revision and enchantment macros have something concrete to target rather than a one-way event stream. `RenderTreeBuilder` *is* an `IRenderOutput`, which is why `Changer.Apply` retargets onto the tree for free.
- **Semantic event channels on `IRenderOutput`** (v2.2 styles, v3D interactive). `PushStyle`/`PopStyle` and `BeginInteractive`/`EndInteractive` are the bracketing primitives game engines map to their native UI — TMP `<link>` + `<b>`, BBCode `[url]` + `[b]`, HTML `<a>` + `<span>`. The interface is the engine-integration contract and should grow additively, by adding parallel bracket pairs, not by reshaping existing methods.
- **Hook-scoped variable stack** (introduced in the divergence audit, matches reference `ts/internaltypes/varscope.ts`). `HarloweVariableStore` keeps temp variables in a stack of dictionaries pushed at every `Visit(HookNode)`; `Set` walks outer-to-inner, writing to the outermost existing declaration. Story vars remain a single flat namespace. `(for:)` iterations, lambda invocations, and nested hooks all rely on this scoping; future slices (especially save/load) must serialise the entire stack rather than a flat dict.

# v1.1 — Slice A: `'s` / `of` / `its` property access

Status: planned, not yet implemented.

## Goal

Make Harlowe's three property-access operators (`'s`, `of`, `its`) functional
at runtime so authors can read fields off datamaps, length/index off arrays
and strings, and use the implicit `it`-bound shorthand. This is the v1.1
gating feature — the moment a story does anything with structured data, it
hits this wall.

## Non-goals

- Lambda-coupled reserved properties (`any`, `all`) — v2, depend on lambdas.
- Range slicing (`$arr's 1stto3rd`) — v2.
- Property assignment (`(set: $person's name to "Bob")`) — v2; out of scope
  even though `to` is implemented for plain variables.
- Dataset support — `DatasetNode` stays "not supported in v1" until proper
  dataset evaluation lands.
- **Ordinal forms (`1st`, `last`, `2ndlast`, etc.) — deferred to a follow-on
  slice (v1.2).** Splits the tokenizer change away from this slice's pure
  evaluator work and keeps the change set tight. Until v1.2 lands, authors
  use numeric indices (`$arr's 1`) and `(length of $arr)` for last-element
  access.

## Background — what's already in place

The tokenizer and parser do most of the work already:

- **Tokenizer** (`HarloweTokenizer`): `'s` is recognized via `TryScanPossessive`
  (whitespace-sensitive — must follow a value-like token); `of` and `its` are
  in `WordOperators`. Verified against the operator table in `CLAUDE.md`.
- **Parser** (`HarloweExpressionParser`):
  - `'s` is in `BinaryOps` at order 3 (data-on-left form).
  - `of` is in `BinaryOps` at order 4 (data-on-right form).
  - `its` is in `UnaryPrefixOps` at order 3.
  - Left-associative, so `$a's b's c` parses as `($a's b)'s c` — the natural
    chained-access reading.

The work is concentrated in `ExpressionEvaluator`. Three new visitor cases,
plus a shared resolver helper.

## Semantics

### `value's accessor`

Evaluate `value` first, then resolve `accessor` against the resulting
container. The resolution rule depends on both the container kind and the
syntactic shape of the accessor (because Harlowe treats a bare identifier
differently from a string-valued expression).

| Container | Accessor shape | Resolution |
|-----------|----------------|------------|
| Datamap | `IdentifierNode("foo")` | look up key `"foo"`; missing key → error |
| Datamap | expression → String | look up by computed key |
| Datamap | expression → anything else | error: "datamap key must be a String" |
| Array | `IdentifierNode("length")` | array count as Number |
| Array | expression → Number | 1-based index; out-of-range → error |
| Array | anything else (including ordinal-shaped identifiers) | error in v1.1; ordinals land in v1.2 |
| String | `IdentifierNode("length")` | char count as Number |
| String | expression → Number | 1-based char index, returned as length-1 String |
| String | anything else | error |
| Number / Bool | any | error: "Number/Bool has no properties" |
| Error | any | propagate the Error unchanged |

Why the syntactic distinction matters: on a Datamap, an identifier `foo` is
a key name, but on an Array/String the same identifier is a *reserved
property* (`length`). The evaluator must inspect the AST shape rather than
just the evaluated accessor value.

### `accessor of value`

Identical semantics to `value's accessor`, just with sides swapped at the
syntactic layer. Implementation detail: handle by recursing into the same
resolver with the operands flipped.

### `its accessor`

Equivalent to `it's accessor`, where `it` is the implicit last value
(`IVariableStore.It`). Look up `it`; if unset, error ("'it' is not yet
set"). Then apply the same resolver as `'s`.

### Error propagation

Every case short-circuits on an `Error` operand and propagates it unchanged.
No exceptions on the runtime path, per the existing error policy.

### Interaction with `it`

The `it` slot is updated by certain operators in Harlowe (mostly the
comparison/identity operators after a variable lookup). Property access
itself does **not** rebind `it` — `'s`/`of` are pure reads. Worth a comment
in the evaluator so a future v2 contributor doesn't add an `it` update by
reflex.

## Implementation outline

### `ResolveProperty` helper

```csharp
private HarloweValue ResolveProperty(HarloweValue container, IExpressionNode accessor)
{
  if (container.IsError) return container;

  // Identifier accessors are resolved against the container's kind first
  // (length/ordinals on arrays/strings; key name on datamaps).
  if (accessor is IdentifierNode id)
  {
    return ResolveIdentifierAccessor(container, id.Name);
  }

  // Otherwise evaluate the accessor as a value and dispatch by container kind.
  var key = Evaluate(accessor);
  if (key.IsError) return key;
  return ResolveValueAccessor(container, key);
}
```

### `ResolveIdentifierAccessor`

- Datamap: `container.AsDatamap.TryGetValue(name, …)`. Missing key →
  `"datamap has no key '<name>'"`.
- Array / String: only `"length"` is honored in v1.1 (plus ordinals if
  scoped in). Anything else → error.
- Number / Bool: error.

### `ResolveValueAccessor`

- Datamap: key must be `String`; otherwise error.
- Array: key must be `Number` and a positive integer 1..N; otherwise error.
  Use 1-based indexing per Harlowe convention.
- String: same as Array but returns a length-1 String of the char at that
  position.
- Number / Bool: error.

### `Visit(BinaryOpNode)` additions

Add branches before the `default`:

```csharp
case "'s":
  _result = ResolveProperty(left, node.Right);
  return;

case "of":
  // `accessor of value` — treat right as the container, left as the accessor
  // node. Right is already evaluated above as `right`; we need the *node*
  // form for left so identifiers are recognized syntactically.
  _result = ResolveProperty(right, node.Left);
  return;
```

A wrinkle: the binary-op handler currently evaluates both sides up-front
before dispatching. For `'s` and `of` we need access to the *unevaluated*
right (or left) AST node, because the `IdentifierNode` shape matters. Two
approaches:

1. **Move `'s`/`of` ahead of the universal eval** at the top of
   `Visit(BinaryOpNode)`, alongside `"to"`/`"into"` which already do this
   (they need the unevaluated target).
2. Keep them in the lower switch and pass `node.Left`/`node.Right` directly
   to `ResolveProperty` (which already accepts the AST node, not the value).

Approach 2 is cleaner — the resolver takes the node and evaluates it
internally only when the syntactic-identifier path doesn't apply. **Use
approach 2.** The pre-eval'd `left`/`right` values can still be reused in
the `IsError` short-circuits at the top.

Actually slight refinement: for the common case (non-error left), we want
`ResolveProperty(left, node.Right)`. So we don't need to skip evaluation —
we just need the right-side *node* in addition to its value. Pattern:

```csharp
case "'s":
  _result = ResolveProperty(left, node.Right);
  return;
```

`right` (the already-evaluated right value) is unused on this branch — fine,
small cost in the common case. Document this in a comment.

### `Visit(UnaryOpNode)` addition

```csharp
case "its":
  var itValue = _store.It;
  if (itValue == null) { _result = HarloweValue.OfError("'it' is not yet set"); return; }
  _result = ResolveProperty(itValue, node.Operand);
  return;
```

Skip the operand-pre-evaluation that the other unary cases do (we need the
node for syntactic dispatch). Restructure the unary handler so it doesn't
unconditionally call `Evaluate(node.Operand)` at the top; instead each case
decides.

## Test plan

### Property access (~18 tests)

Group in a new `region "Property access ('s, of, its)"` in
`ExpressionEvaluatorTests`.

Datamap:
1. `(dm: "name", "Bob")'s name` → `"Bob"` (identifier accessor)
2. `(dm: "name", "Bob")'s "name"` → `"Bob"` (string accessor)
3. `(dm: "name", "Bob")'s missing` → Error mentioning "key"
4. `(dm: "n", "B")'s 5` → Error: "key must be a String"
5. `name of (dm: "name", "Bob")` → `"Bob"` (`of` reversal)
6. Nested: `(dm: "p", (dm: "hp", 10))'s p's hp` → `10`

Array:
7. `(a: 10, 20, 30)'s length` → `3`
8. `(a: 10, 20, 30)'s 1` → `10`
9. `(a: 10, 20, 30)'s 3` → `30`
10. `(a: 10, 20, 30)'s 4` → Error: out of range
11. `(a: 10)'s "x"` → Error
12. `length of (a: 1, 2)` → `2`

String:
13. `"hello"'s length` → `5`
14. `"hello"'s 1` → `"h"`
15. `"hello"'s 6` → Error
16. `"hello"'s notalength` → Error

`its` shorthand:
17. After `$x to (dm: "name", "Bob")`, `(if: its name is "Bob")[…]`
    renders the hook. (Uses `it`, set by `to`; need to confirm the
    evaluator does set `it` on `to`. If it doesn't, this test goes via
    direct store seeding instead.)

Errors:
18. Property access on a Number: `(if: 5's length is 0)` → Error renders.

## Open questions to resolve before implementation

1. **What does `(a: 1, 2)'s 0` return?**
   Harlowe is 1-based. 0 should be an out-of-range error, not the first
   element. Same for negative.

2. **String char access — return type?**
   Harlowe returns a single-char String, not a code point or character
   primitive. We mirror that.

3. **Does `to`/`into` set `it`?**
   The evaluator currently sets `it` via `IVariableStore.Set` (which updates
   the It slot). Confirm this still holds during the property-access tests
   that use `its` after a `to`. If not, the `its` test seeds the store
   directly.

4. **Naming of helper methods in the evaluator?**
   `ResolveProperty`, `ResolveIdentifierAccessor`, `ResolveValueAccessor` —
   default. If the team prefers `Access*` naming, swap.

## Risks / unknowns

- **The `is`/`is not` `it`-update semantics** I haven't audited carefully —
  if `it` updating is more than what the store does on `Set`, the `its`
  test may need different seeding. Worst case: drop the `its`-after-`to`
  test and keep only direct-store-seeding tests.
- **Chained access semantics for missing intermediate keys.** Harlowe
  returns an error and the chain stops; the resolver's error short-circuit
  already handles this, but the test for nested datamap access (#6) is
  worth keeping precisely to lock in the behavior.
- **Identifier collision with reserved names on datamaps.** If a datamap
  has a key literally named `"length"`, `$map's length` should return that
  key's value (datamaps win over reserved-name dispatch). The resolver
  table above reflects this, but it's worth a deliberate test case if we
  want to lock the behavior.

## Deferred to v1.2 — ordinal support

Ordinal forms (`1st`, `2nd`, `3rd`, `Nth`, `last`, `2ndlast`, etc.) are a
follow-on slice. Splitting them out keeps slice A as pure evaluator work and
isolates the tokenizer change in its own slice for risk-isolation reasons.

When v1.2 lands it will add:
- `HarloweParser/Tokens/HarloweTokenizer.cs` — `TryScanOrdinal` recognizing
  `\d+(st|nd|rd|th)` plus `last` and `Nthlast`. Special-case the digit-
  leading path the way `TryScanTwoBind` already does.
- Reuse of `TokenType.Identifier` with the ordinal text as the `Value` —
  no new token type needed; the resolver already special-cases identifier
  accessors and just gets a few extra entries (`1st`, `last`, etc.) on the
  Array/String dispatch tables.
- Tokenizer tests for `1st`/`2nd`/`3rd`/`last`/`2ndlast` recognition plus
  the negative case (`1stnotwhole` shouldn't fuse).
- Evaluator tests for `(a: 10, 20)'s 1st` → `10`, `(a: 10, 20)'s last` →
  `20`, `"hello"'s 1st` → `"h"`, etc.

Estimated effort: ~half a day on top of slice A landing. No design
questions blocked on it.

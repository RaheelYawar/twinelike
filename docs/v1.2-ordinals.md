# v1.2 — Ordinal indexing

Status: planned, not yet implemented.

## Goal

Make Harlowe's ordinal accessors (`1st`, `2nd`, `3rd`, `Nth`, `last`,
`2ndlast`, etc.) functional on arrays and strings so authors can write
`$arr's 1st` and `"hello"'s last` instead of falling back to numeric
indexing and `(length:)` arithmetic.

Split off from v1.1 slice A to isolate the tokenizer change in its own
slice for risk-isolation reasons. Until v1.2 lands, authors use numeric
indices (`$arr's 1`) and `(length: …)` for last-element access.

## Background — what's already in place

After v1.1 slice A:
- `ExpressionEvaluator` resolves identifier accessors syntactically via
  `ResolveIdentifierAccessor(container, name)` — currently only `length`
  is honored on Array/String. Adding ordinals is a few more entries on
  the same dispatch path, no structural change.
- `'s`, `of`, and `its` are wired up at the parser and evaluator level.
- Numeric indexing (`$arr's 1`) is 1-based and shares
  `IndexArray`/`IndexString` helpers — ordinals can reuse these.

The work is concentrated in two places: tokenizer recognition of the
ordinal forms, and a handful of new entries in
`ResolveIdentifierAccessor`.

## Files touched

- `HarloweParser/Tokens/HarloweTokenizer.cs` — add `TryScanOrdinal` that
  recognizes `\d+(st|nd|rd|th)` plus `last` and `Nthlast`. Special-case
  the digit-leading path the way `TryScanTwoBind` already does.
- `HarloweParser/Runtime/ExpressionEvaluator.cs` — extend
  `ResolveIdentifierAccessor` with cases for `1st`/`Nth` (parse digits,
  reuse `IndexArray`/`IndexString`), `last` (last element), `2ndlast`/`Nthlast`
  (last - N + 1).
- `HarloweParser.Tests/HarloweTokenizerTests.cs` — recognition tests for
  `1st`/`2nd`/`3rd`/`last`/`2ndlast` plus negatives (e.g. `1stnotwhole`
  should not fuse into a single token).
- `HarloweParser.Tests/Runtime/ExpressionEvaluatorTests.cs` — evaluator
  tests for `(a: 10, 20)'s 1st` → `10`, `(a: 10, 20)'s last` → `20`,
  `"hello"'s 1st` → `"h"`, `"hello"'s 2ndlast` → `"l"`, out-of-range
  errors, and ordinal access on a non-collection.

## Token shape

Reuse `TokenType.Identifier` with the ordinal text as the token's
`Value`. No new token type — the resolver already special-cases
identifier accessors and just gets a few extra entries on the
Array/String dispatch tables.
